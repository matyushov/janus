Give any app a local SMB share backed by storage you control.

janus serves SMB 3.1.1 on 127.0.0.1 and sends everything written to it to the backend you choose, over a secure channel. The client sees an ordinary disk. The network sees one authenticated stream. No Samba, no kernel extension, no SMB port open on your network.

The idea

SMB is everywhere. It is also built for a trusted LAN.

Operating systems, backup tools and plenty of legacy software know how to write to a network drive, and the network drive speaks SMB. Exposing an SMB service to reach remote storage means an attack surface, legacy authentication and protocol quirks. janus keeps the convenient half of SMB and drops the dangerous half.

face one

Clients see an ordinary share

Anything that can mount smb://127.0.0.1/… works with files as usual. janus adapts to each client's expectations with a per-share profile, so a client's quirks stay out of the core.

face two

The storage is a plug-in

Behind the share sits a backend: your own receiver over mutual TLS today, a plain folder for development, object storage under study. The network carries one authenticated stream and no SMB at all.

the name

Janus, the god of doors

One face looks at the SMB client, the other at the storage. The code that stands between them is the whole project.

Use cases

One transport, several jobs

Time Machine is the first client janus fully supports, because it is the hardest one: if it works, plain file copies are easy. It is a mode of the project, not its purpose. Every card below says honestly how far along it is.

works

Backups from macOS to your own server

Time Machine writes into the loopback share; janus carries the sparsebundle to a server you run. Full and incremental backups, file restore and short outages are verified end to end.

works

Storage for your own application

Start the client inside your C++ program through a small C library, mount the share and use plain files, with the journal and the secure link taken care of. See Embed.

works with macOS clients

Remote storage for SMB-only software

Programs that only know "save to a network drive" get a remote, authenticated destination without an SMB service on the network. File copies through mount_smbfs and NetFS are verified byte for byte.

planned

Windows clients

File History, robocopy, wbadmin. A compatibility profile exists in the code; it has not been tested against real Windows clients yet.

planned

Linux clients

cifs.ko and smbclient. There is a known gap in session setup that must be closed first.

researching

S3, MinIO and similar backends

The backend interface is ready for them. Large sparse files make "one file, one object" a poor fit, so a chunked layout is being evaluated. Nothing ships yet.

How it works

A strict SMB server on one side, a careful uploader on the other

janus-smbd runs next to the client, on the same machine. janus-receiverd runs where the data is kept. Everything on the left of the dashed line stays on the client's machine.

  1. The client writes into a loopback share. janus-smbd is a purpose-built SMB 3.1.1 server, written from scratch in Rust. It requires signing and accepts no guests. A per-share profile switches on only the behaviour a given client needs.
  2. Every write lands in a local journal first. The write is acknowledged as soon as it is safe on the local disk, so the speed of the client is not tied to the round trip to the server.
  3. An uploader moves the journal to the receiver. Writes are idempotent (they carry offsets), so a retry after a dropped connection is always safe. Ranges overwritten before upload are merged, so the network carries the final bytes only.
  4. The receiver files everything under the client's identity. The certificate decides which machine you are, which directory you may touch and how much quota you have. A client never names a path outside its own store.
  5. fsync stays honest. When a client asks for a full flush, janus does not answer until the data has really reached the receiver. "Saved" never means "still only on this machine".
What is inside

The parts that make it a dependable destination

An SMB server of its own

SMB 3.1.1 with signing, NTLMv2, durable handles V2 that survive a daemon restart, lease V2 with break acknowledgements, interim STATUS_PENDING and CANCEL. Nothing is borrowed from Samba.

Client profiles

Behaviour is chosen by capabilities, never by operating system: TIME_MACHINE today, WINDOWS_GENERIC and POSIX_GENERIC next. Apple's extensions are on only where they are needed.

Pluggable storage backends

One small interface (open, read, write, flush, rename, list, free space). The same contract tests run against a local folder and against the gRPC receiver, so backends behave alike.

Survives a dead server, for a while

Slow or missing replies become interim responses instead of errors, so a stalled receiver does not break the client's I/O. Time Machine, the strictest client we tried, tolerates about two minutes.

Many machines, one receiver

Each client certificate maps to its own store and quota. One machine cannot read, list or write another's files, not even with .. or absolute paths.

Embeddable and observable

A C library with a header-only C++ wrapper runs the client in-process. janus-cli client status --watch and client logs -f show backlog, errors and waiting operations.

Proof

The hardest client first, tested against the real thing

macOS Time Machine is picky: Apple's SMB extensions, durable handles, leases and full-flush semantics that no open, non-GPL SMB server offers. The numbers below come from a real backupd in a macOS 26 virtual machine writing through janus to a Linux receiver on another machine. Throughput was measured over home Wi-Fi, so read it as "the link is the limit", not as a benchmark.

Use it in your own application

Start the client inside any C++ program

libjanus exposes eleven C functions and a header-only C++ wrapper. Your application starts the client in its own process, mounts the loopback share and works with plain files.

  1. Link it. find_package(janus CONFIG REQUIRED), then janus::client_static or janus::client_shared; pkg-config files are installed too.
  2. Describe the share. Where the receiver is, which certificate identifies this machine, where to keep state.
  3. Start. The loopback SMB endpoint, the journal and the TLS link come up inside your process.
  4. Mount. mount_info() returns the URL and credentials; on macOS a helper mounts it through NetFS.
  5. Stop. Optionally wait until the journal has reached the receiver.
// C++17, header only wrapper over the C ABI
#include <janus/janus.hpp>

janus::Config config;
config.state_dir = "/var/lib/myapp/janus";                 // journal, credentials
config.share.appliance_endpoint = "backup.example.org:7443";
config.share.client_cert_path   = "client.pem";
config.share.client_key_path    = "client.key";
config.share.ca_pem             = read_file("ca.pem");

janus::Client client = janus::Client::start(config);       // runs inside your process
janus::MountInfo info = client.mount_info();               // smb://127.0.0.1:<port>/backup, user, password

// mount info.url (macOS: <janus/mount_macos.hpp>), then use ordinary files

client.stop();                                             // stop(timeout) first waits for the upload

Five runnable examples live in examples/: the life cycle, mounting and copying with a checksum, watching the journal drain, an exception-free API and configuring later. The library rules (threads, memory ownership, error codes) are in the janus-ffi README.

Security model

What is protected, and what is not

A transport that over-promises is worse than none. This is the honest list.

Protected

  • SMB is served on loopback only and never reaches the network.
  • The network link is TLS 1.3 with mandatory client certificates; plain gRPC is refused at start-up outside development mode.
  • SMB messages are signed; guest access does not exist.
  • Each machine is confined to its own store and quota on the receiver.
  • Journal and credential files are private to the user (mode 0600/0700).
  • An interrupted upload resumes without duplicates or holes, even after kill -9.

Not protected (yet)

  • janus does not encrypt file contents itself. Use the client's own encryption (for Time Machine, its backup encryption) and full-disk encryption on the receiver.
  • The journal on the client machine is plaintext at rest.
  • There is no certificate revocation: removing a machine means editing the receiver's machine list.
  • The development PKI scripts are for development only; keeping a CA key safe is your job.
  • Anyone who owns the receiver owns the stored data.
  • No independent security audit has been done.

Get started

Try the whole path on one machine

You need Rust (the repository pins the version), CMake and a C++ compiler. This starts a throw-away receiver with a throw-away certificate authority, then mounts a share through the embedded client and copies a file with a checksum. 

# terminal 1: a receiver on 127.0.0.1 with a development PKI
examples/run-local-receiver.sh /tmp/janus-demo

# terminal 2: build the examples and run the mount-and-copy one
cmake -S examples -B build/examples
cmake --build build/examples
source /tmp/janus-demo/env.sh
./build/examples/02_mount_and_copy

For a complete Time Machine lab (a macOS guest, a receiver on another machine, restore from Recovery) see tools/lab. The lab scripts change Time Machine settings; read them before running them on a machine whose backups you care about.
